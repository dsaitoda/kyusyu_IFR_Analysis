# 九州 ADS-B 航跡「欠損・再出現」調査キット

これは **2026-10-17（日本時間）** の九州周辺における ADSB.lol の過去データを使い、位置記録の途絶を調査するプログラムです。**2026-10-17の実機データについて、集計処理はまだ行っていません。** こちらで検証したのは合成した試験用の航跡のみです。

## 解析の定義

- 範囲：緯度29.2〜34.7度、経度128.0〜133.4度（九州周辺を囲む矩形であり、管制空域の境界ではありません）。
- 時刻：2026-10-17 00:00〜24:00 JST（2026-10-16 15:00〜2026-10-17 15:00 UTC）。
- 対象：最初は全航空機。IFR/VFRの確実な分類はしません。
- データ：時刻・緯度・経度・気圧高度を機体別に時系列で整理します。**高度で点を削除してからギャップを判定しない**ため、高度10,000 ftへの出入りは「欠損」にしません。
- ギャップ：同じ ICAO アドレスの連続位置点が60秒より長く空いた場合を候補とします。1〜3分、3〜10分、10分超に分けます。
- 「空港付近で再出現」候補：3分超のギャップで、ギャップ両端とも500 ft超かつ10,000 ft以下、再出現点が登録空港の基準座標から20 NM以内。これだけでは着陸やIFR進入を証明しません。
- **解析矩形の外を通過した点も、該当機体については維持**して比較します。矩形の外へ出たために見かけ上生じたギャップを排除します。
- readsb の「新しい飛行レグ」フラグがあればその区間を連続性の分母から除外します。
- 既に飛行を終えた後の再離陸、収集サービスの間引きや受信機の地理的遮蔽などは完全に判別できません。

## A. GitHub Actions で自動ダウンロード・解析（推奨）

1. 新しい GitHub リポジトリを用意します（公開/非公開どちらでも可能）。このキットの `kyushu_continuity.py`, `download_release.py`, `.github/workflows/analyze.yml` を**パス構造を保ったまま**アップロードします。
2. リポジトリの **Actions** → **Kyushu ADS-B continuity analysis** → **Run workflow** を押します。
3. `date_jst` に `2026-10-17` と入力し実行します。
4. 終了したら、該当ワークフロー実行ページの **Artifacts** から `kyushu-continuity-2026-10-17` を取得します。
5. `summary.txt`（集計結果）、`gap_events.csv`（候補の全イベント）、`gap_points_below_10000ft.kml`（Google Earthで確認）、`gap_histogram.png`（高度10,000 ft以下の分布）を参照してください。

**注意：** 1回の実行で世界全体の複数GBのデータをダウンロード（分割数・総容量は日付によって変わります）します。GitHub側の使用時間・ストレージ容量・転送制限・無料枠には注意してください。データを公開しているのは ADSB.lol で、GitHub Actions が遅延・失敗する場合もあります。

## B. Windows / Spyder で実行する

1. 次の2日分の GitHub Releases から **各日にある `.tar.aa` / `.tar.ab` / `.tar.ac` など全パーツ** をダウンロードして、`C:\ADSB_History` に保存します。`.aa`/`.ab` は解凍・結合しないでください。
   - https://github.com/adsblol/globe_history_2026/releases/tag/v2026.10.16-planes-readsb-prod-0
   - https://github.com/adsblol/globe_history_2026/releases/tag/v2026.10.17-planes-readsb-prod-0
2. `kyushu_continuity.py` 冒頭の `INPUT_DIR`, `OUTPUT_DIR`, `TARGET_DATE_JST` を必要に応じて変更します。
3. Spyder上で実行します。標準ライブラリのみで集計できます。`gap_histogram.png` が必要な場合のみ `matplotlib` が必要です。
4. 完了後は `results` フォルダを確認してください。`positions.sqlite` は中間データで、大きくなることがあります。

※ GitHub Actions と同じ形式で Windows 側でも自動ダウンロードしたい場合は、`python download_release.py --date 2026-10-17 --directory "C:\ADSB_History"` を使えます（要 `curl`）。配布元の GitHub API にあるアセット一覧を取得し、全パーツのサイズ・SHA-256を確認してから解析します。

## 出力ファイル

| ファイル | 内容 |
| --- | --- |
| `summary.txt` | 全航空機数・高度10,000ft以下の連続点ペア数・各時間ギャップ件数 |
| `summary.csv` | 同様の件数を機械読み取りできる形式で保存 |
| `gap_events.csv` | 欠損前後の時刻・位置・高度・経過時間・直線距離・直線移動を仮定した対地速度・最寄空港と距離・位置情報staleフラグ |

| `positions.sqlite` | 調査に利用した時系列データベース（GitHub Actionsではアップロードしない） |

## 品質上の留意点

- 記録が全くなかった航空機はデータから存在を知ることができないため、ここで求める比率は**ADSB.lolが少なくとも一度観測した航空機を母集団**とする限定的なものです。航空交通全体の欠測率ではありません。
- ADSB.lol の readsb trace は一定間隔で間引いて保存される可能性があり、元の受信点列とは限りません。`stale` フラグも参考にします。
- 同じ ICAO アドレスで複数レグの飛行が連続する場合は、検出フラグが必ずしも完璧ではありません。
- `altitude` は基本的に気圧高度であり、空港の標高を引いた対地高度 (AGL) ではありません。
- 機種やコールサインが欠けている機体もあります。IFRの分類や安全な飛行経路の判断には、別の運航情報・航空情報・管制状況を必ず用いてください。
- 配布元のライセンス：ODbL 1.0。公開・再配布時にはその条件を確認してください。

## 分割ファイル数について（修正 2026-10-18）

日付によって分割数は異なります。例えば 2026-10-15 (UTC) は `.aa`, `.ab`, `.ac` の3本です。従来の「常に2本」という前提では末尾が欠落し、`tarfile.ReadError: unexpected end of data` となります。現在はGitHub Releases APIから全パーツを自動検出・照合し、パーツ数を記録した `.tar.manifest.json` を保存します。`Run workflow` の `date_jst` は **日本時間** で指定してください。前回ログは10月16日を選んでいました。
